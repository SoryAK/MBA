# ADR 0107: `mba start` / `mba stop` and the generated user unit

- **Status:** Accepted
- **Date:** 2026-09-13
- **Deciders:** project maintainer + agent
- **Tags:** mba, cli, daemon, systemd, lifecycle
- **Relates to:** ADR-0092 (daemon as orchestrator), ADR-0096 (CLI is a thin door), ADR-0097 (daemon owns *model* server lifecycle)

## Context and Problem Statement

ADR-0096 made `mba` a thin client of a running daemon. That left no Ollama-like
verb. `npm install` does not start MBA. Operators started the service with
`npm run start:service` / `tsx src/service/main.ts`, which holds a terminal, or
with a hand-rolled `~/.config/systemd/user/mba.service` that pointed at one
checkout and one Node (nvm PATH, CUDA/HSA env).

MBA is meant to stay up while you use the machine. A held terminal is debug, not
the product. A unit that hard-codes last month’s checkout will boot the wrong
binary after `npm link`.

ADR-0097 is the *model inference* server (llama.cpp today). This ADR is the
**MBA daemon** itself — the process that owns the store, the watch, and the
proxy.

## Decision Drivers

- **Background is normal.** The operator’s terminal is free after start.
- **This install.** ExecStart is the Node that ran `mba start` and this
  package’s daemon entry (tsx from source, or `dist/service/main.js` after
  build).
- **Same supervisor as the hand-rolled unit.** `Type=simple`,
  `Restart=on-failure`. A clean `mba stop` stays down.
- **Machine env is not in git.** CUDA / ROCm / `HSA_OVERRIDE_GFX_VERSION` live
  on the box. `mba start` must not wipe them.
- **Idempotent start.** A second `mba start` prints the URL already in use. A
  live pid that is not answering is refuse, not a second spawn.
- **Thin-client rule stands.** Only start/stop (and `--help`, `completion`,
  `estimate-memory`) may run with the daemon down.

## Considered Options

- **Option A — Keep `npm run start:service` as the verb.** Rejected. That is a
  checkout script, not an operator door, and it holds the terminal.
- **Option B — Always `--foreground`.** Rejected as the default. Fine for
  debug; it is not how the product runs.
- **Option C — System-level systemd / launchd / Windows service.** Rejected for
  v1. MBA is per-user state under the operator’s home. A user unit matches that.
- **Option D — Detached spawn only (no supervisor).** Rejected as the Linux
  default. No restart-on-crash, no linger, easy to leak a pid.
- **Option E — Generate a systemd `--user` unit; detached spawn if there is no
  user systemd; `--foreground` is this process.** Accepted.

## Decision

**`mba start` runs the daemon in the background. `mba stop` stops it.**

### Linux with user systemd

`mba start` writes `~/.config/systemd/user/mba.service` (marker:
`# Generated by mba start.`), `daemon-reload`, `enable --now`. ExecStart is
this install’s node + `service/main` (`.ts` via tsx, or `.js` after build).
PATH includes the node that ran `mba start` (nvm-safe).

`Restart=on-failure`. `mba stop` is `systemctl --user stop mba`, so a clean
stop does not come back.

First replace of a **non-generated** unit copies extra `Environment=` lines
(not PATH) into `mba.service.d/local.conf` and will not overwrite that drop-in
again. Machine GPU env stays local.

`loginctl enable-linger` is attempted and ignored on failure. The unit still
runs while the user is logged in.

### No user systemd

Detached spawn of the same entry. `mba stop` SIGTERMs the discovery pid.

### `--foreground`

This process **is** the daemon. No unit, no detach. Logs stay in this terminal.

### Already running / stale

| Discovery | Action |
| --- | --- |
| pid alive and `/status` answers | print URL, do not spawn |
| pid alive, not answering | refuse (do not start a second daemon) |
| no pid / dead | start |

Code: `packages/core/src/cli/start.ts`, `systemd-user.ts`. Package scripts:
`start` → `mba start`; `dev` → `mba start --foreground`.

## Consequences

### Positive

- One verb for “the daemon is up,” the same shape as a model host, without MBA
  becoming a host.
- The generated unit tracks this install; the drop-in keeps box-specific env.
- ADR-0096 stays true for every other verb.

### Negative / deferred

- No launchd or Windows service. Those platforms get detached spawn until a
  later ADR.
- First `mba start` on a machine with a hand-rolled unit **replaces** that
  unit (after copying extra env once). Operators who customized ExecStart must
  use the drop-in or a wrapper.
- Linger failure is silent; a reboot without linger will not bring the daemon
  back until login or another `mba start`.

## Relationship to other ADRs

- **ADR-0096:** Start/stop are the documented exception to “CLI talks to a
  running service.” This ADR is that exception.
- **ADR-0097:** Model inference server boot/stop/slots. Not this process.
- **ADR-0092:** The daemon remains the orchestrator; this ADR is only how it
  stays running.
